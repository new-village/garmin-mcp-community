# garmin-mcp-community 仕様ドラフト

作成：2026-11-23（Niimura の要件をもとに ちいかわ が整理。未決定事項は末尾）
状態：仕様 v1（Niimura 要件＋委任分の定義まで完了）。リポジトリはまだ作成しない（本仕様の確認後）。

## 1. 目的

Garmin Connect の健康・トレーニングデータを、AIエージェント（Muse 等）が MCP 経由で参照できるようにする、非公式・コミュニティ maintained な MCP サーバー。AI が体調管理のアドバイスやトレーニングのスケジュール管理をしやすい形で情報を渡すことを重視する。

## 2. Niimura の要件（2026-11-23）

1. Google Cloud Run 上の Web サービスとして運用する
2. セッション情報は MCP サーバー側で保持しない。エージェント（クライアント）側が保持し、認証画面を開いて取得する形にする（ステートレス設計）
3. 不特定多数の人が使える形にする（個人専用にしない。マルチユーザー前提）
4. 日常的に見る指標が AI 側で参照できること：ストレス、Body Battery、睡眠、運動量、ステップ数 など
5. AI がトレーニングのスケジュール管理や体調管理のアドバイスをしやすいように情報連携する

## 3. 設計への落とし込み

### 3.1 配置・運用
- Cloud Run（GCP プロジェクト kuro-intelligence、リージョンは asia-northeast1 想定）
- MCP トランスポートは Streamable HTTP（Web サービスとして公開）
- ステートレス：Cloud Run のインスタンスにセッションも健康データも残さない。リクエスト毎に完結する

### 3.2 認証・セッション（最重要論点）
- Garmin には個人向け公式 OAuth API がないため、非公式ライブラリ garminconnect のトークン方式を使う前提
- フロー案：
  1. 利用者は認証画面（Web）で Garmin にログインし、トークンを取得する（MFA があればその場で処理）
  2. トークンはエージェント（クライアント）側が保持する。MCP サーバーは保持しない
  3. MCP 呼び出し時にトークンをリクエストヘッダーで渡し、サーバーはそのリクエスト内でのみ使って Garmin API を呼ぶ
- サーバー側の禁止事項：トークンと健康データをログに残さない、DB に保存しない、キャッシュしない（メモリ内でもリクエストを跨がない）
- 未決：トークンの具体的な受け渡し形式（カスタムヘッダー名、MCP の OAuth 2.1 仕様に寄せるか）、トークン失効時の再認証フロー、認証画面をこのサービスに含めるか別にするか

### 3.3 マルチユーザー
- ユーザー登録・ユーザー DB を持たない（持つと健康データ管理責任が発生するため、v1 では持たない）
- 同時アクセスは Cloud Run のスケールに任せる。Garmin 側のレート制限・非公式エンドポイントの仕様変更リスクは利用者側のトークン単位で閉じる

### 3.4 ツール設計（読み取り専用から）
生データをそのまま返すだけでなく、AI がアドバイスに使いやすい粒度のツールを用意する。

日次系：
- get_daily_summary(date) — ステップ数、運動量（カロリー・運動時間）、安静時心拍などを 1 日分に要約
- get_sleep(date) — 睡眠時間、スコア、ステージ内訳
- get_stress(date) — ストレスレベルの推移・平均
- get_body_battery(date) — Body Battery の推移、朝の充電量と就寝時の残量

期間・トレンド系（アドバイスの要）：
- get_trends(days または start/end) — 睡眠・ストレス・Body Battery・安静時心拍・歩数の期間平均と傾向
- get_recovery_status(date) — 睡眠 + Body Battery + ストレス + 安静時心拍を合成した、その日のコンディション要約

トレーニング系：
- get_activities(start/end) — アクティビティ一覧（種目、時間、距離、心拍、カロリー、トレーニング効果）
- get_activity_detail(id) — 個別の詳細

共通ルール：
- 日付は利用者のタイムゾーン前提で扱い、レスポンスに日付とタイムゾーンを明記する
- 単位を明記する（歩、kcal、分、ms など）。AI が誤読しない形にする
- 書き込み系（ワークアウト作成・スケジュール登録など）は v1 では扱わない。スケジュール管理は「AI 側が計画を持ち、本 MCP は実績と体調を返す」分担を初期案とする

## 4. 非機能・注意

- 非公式エンドポイント依存：Garmin 側の仕様変更で壊れる可能性があることを README に明記する
- 医療アドバイスではないことの位置づけ：体調管理の参考情報であり、診断はしない
- 公開サービスとして出す場合のプライバシー説明（データ非保持の設計そのものが説明材料になる）

## 5. 残りの定義（2026-11-23、Niimura の委任により ちいかわ が定義）

Niimura の要件リストは上記で完結。以下は委任を受けて定義した初期案で、Niimura の veto があれば変更する。

### 5.1 認証フローとトークン受け渡し
- 認証画面は本サービス内に置く（`/auth`）。利用者がそこで Garmin にログインし（MFA はその場で処理）、トークンを発行する
- ログイン処理の間だけ一時的な状態をメモリに持つが、発行後はサーバー側に何も残さない。トークンは利用者（エージェント側）に一度だけ返して終わり
- トークン形式：garminconnect（garth）の OAuth トークン一式を JSON 化したもの
- MCP 呼び出し時は `Authorization: Bearer <token>` ヘッダーで渡す（MCP の認証作法に寄せる）
- トークンが失効していた場合、サーバーはリクエスト内でリフレッシュを試み、更新されたトークンをレスポンスヘッダー（`X-Garmin-Token`）で返す。エージェント側はそれで保持トークンを差し替える
- リフレッシュも失敗した場合は 401 を返し、再認証（`/auth`）を案内する
- サーバーは Authorization ヘッダーと健康データを一切ログに残さない。アクセスログも最小限にする

### 5.2 トレーニングのスケジュール管理
- v1 は読み取り専用に留める。計画（スケジュール）は AI 側が持ち、本 MCP は実績（アクティビティ）と体調（回復状態）を返す
- Garmin カレンダー／ワークアウトへの書き込みは v2 の検討事項とする（非公式 API の書き込みは壊れやすく、誤登録の影響も大きいため）

### 5.3 公開形態
- 主形態は OSS：誰でも自分の Cloud Run 等にセルフホストできる形で公開する
- 併せて、kuro-intelligence 上に公式ホスト済みインスタンスを 1 つ運用する。ステートレス設計のため、他人のトークン・データを預からずに提供できる
- ライセンスは他の *-mcp-community リポジトリと揃える

### 5.4 対応クライアント
- Muse 専用にしない。MCP（Streamable HTTP）汎用とし、Bearer トークンを付けられるクライアントなら使える

### 5.5 ツール一覧（v1 確定）
- get_user_profile — 表示名とタイムゾーン（日付解釈の基準）
- get_daily_summary(date) — ステップ数、消費カロリー、運動量（強度別分数）、安静時心拍
- get_sleep(date) — 睡眠時間、スコア、ステージ内訳
- get_stress(date) — 平均・最大、推移の要約
- get_body_battery(date) — 推移、朝の値と就寝時の値、充電量
- get_heart_rate(date) — 安静時心拍と推移の要約
- get_activities(start, end) — アクティビティ一覧（種目、時間、距離、心拍、カロリー、トレーニング効果）
- get_activity_detail(id) — 個別詳細
- get_trends(days, 最大 90 日) — 睡眠・ストレス・Body Battery・安静時心拍・歩数の期間平均と傾向
- get_recovery_status(date) — 睡眠 + Body Battery + ストレス + 安静時心拍の合成コンディション要約

共通仕様：
- 日付は利用者のタイムゾーン（プロファイル準拠）で解釈し、レスポンスに日付・タイムゾーン・単位を必ず含める
- 期間指定には上限を設ける（トレンド 90 日、アクティビティ一覧 100 件）
- エラーは AI が判断できる形で返す（401=再認証、404=データなし、502/503=Garmin 側障害、429=レート制限）

### 5.6 技術構成（初期案）
- Python + FastMCP（garminconnect が Python のため）
- Dockerfile で Cloud Run にデプロイ。GitHub push → GitHub Actions（Workload Identity、鍵なし）→ Cloud Run の自動デプロイ
- 設定は環境変数のみ。秘密情報はサーバー側に置かない（トークンは前述のとおりクライアント保持）
